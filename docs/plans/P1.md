# P1 plan: scaffold, tasks, restricted test execution

Written before implementation, 2026-10-16. Scope: P1 only; no inference,
energy measurements, difficulty assignment, or owner-written analysis.

## Files
- Scaffold: README.md, .gitignore, pyproject.toml, requirements.txt;
  src/prompt_energy/, experiments/, analysis/, results/, tests/.
- experiments/config.py: frozen model tags, seven prompt conditions (P3 has

- data/: original HumanEval archive, MIT notice, revision/checksum provenance.
- src/prompt_energy/tasks.py: validate archive and task records, load selection.
- src/prompt_energy/policy.py, worker.py, sandbox.py, windows_job.py:

## Design
Use Python 3.11 in a project virtual environment. Pin the fixed-stack libraries
and the requested pytest/ruff tools; use stdlib ctypes for Windows controls so
the sandbox needs no new dependency. Do not run candidate code in the parent.

Check the HumanEval MIT licence before obtaining the dataset. Pin an upstream
Git revision and SHA-256; preserve the unmodified archive and licence. Sample
40 from numeric task-ID order with a local random.Random seed, store explicit
IDs in config and verify the selection. Never replace a difficult/failed task.
Use original synthetic few-shot examples, independent of benchmark solutions.

Each candidate runs in an isolated Python subprocess (-I -S -B) in a fresh
temporary directory with an allowlisted environment, no inherited stdin or
captured unbounded output. AST checks allow only selected computation imports,
block dangerous names, private attributes and dynamic execution. The worker
uses restricted builtins and separate candidate/test namespaces. The parent
places the waiting worker in a Windows Job Object before releasing it: one
process, hard memory cap, kill-on-close. Parent polls memory and a monotonic
deadline; timeout terminates and reaps the worker. Fail closed if isolation
setup fails. Return structured outcomes including rejection, assertion,
runtime error, timeout, memory and infrastructure failure.

## Risks
- Python-level filtering is not a security boundary against determined hostile
  code. Windows Job Objects bound resources, not filesystem/network authority.
  Document this explicitly; use an offline disposable VM for adversarial code.
- Restricting imports can reject valid solutions; report policy rejections,
  never silently count them as ordinary incorrect answers or drop tasks.
- Tiny generation windows and benchmark contamination remain study limitations.
- Existing working agreement describes a different project; SPEC is authoritative.
- Python 3.11 is not registered on this host; provision locally if possible and
  report any inability to meet the specified environment.
- Balanced power scheme is observed; AC connection and Windows power-mode UI
  setting must be distinguished from the scheme and never invented.
