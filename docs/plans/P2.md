# P2 plan — local inference and auditable correctness

Scope: P2 only. Python 3.13.7, existing dependencies and the accepted P1 runner.
No energy collection, difficulty grouping, or full study run. Owner review of
PROMPTS.md and the proposed settings below is required before any generation,
including warm-up and determinism calls.

## Runtime and settings proposed for registration

Use Ollama's local HTTP API via Python's standard-library HTTP client: Windows
support, runtime-reported token counts/durations, explicit seed/temperature, and
no heavyweight Python inference dependency. Use /api/generate with stream=false.

- Models: qwen2.5-coder:0.5b and qwen2.5-coder:1.5b.
- Temperature 0; seed 1729; output-token budget num_predict=768 for every arm.
- Proposed context size: num_ctx=4096, fixed across models and arms.
- Proposed CPU threads: num_thread=8; num_gpu=0; sequential requests.
- keep_alive=-1 while running; identical empty custom stop list, preserving the
  model's native end-of-sequence behavior. Record the runtime template and digest.
- Proposed generation request timeout: 300 seconds. Never silently retry a failed
  generation; persist failures so they remain part of the audit trail.
- Smoke: first five already registered IDs (0, 1, 11, 13, 14), seven arms, 1.5b,
  one repeat = 35 scored generations. No sample selection based on outcomes.
- Seeded shuffled order across task/prompt combinations; persist the complete
  schedule before the first call so resume cannot reshuffle remaining jobs.
- One synthetic warm-up per model per process session, excluded from scored rows
  but saved and labelled in raw JSONL. Record load_duration separately for every
  response, not just warm-up. Keeping a model resident does not guarantee zero
  load overhead; actual API fields remain authoritative.
- Determinism check: two identical requests for the first smoke task and P0,
  separately labelled and excluded from scored rows; compare exact response text
  and report whether it matches. Never assume temperature zero guarantees identity.

## Files and design

- docs/PROMPTS.md: exact system/user templates and original demonstrations for
  owner review. experiments/config.py remains the executable registration.
- src/prompt_energy/prompts.py: deterministic assembly without solutions/tests.
- src/prompt_energy/ollama.py: loopback-only HTTP, model/version inspection,
  explicit options, response validation and direct API token/duration accounting.
- src/prompt_energy/extraction.py: one rule applied identically to every arm.
- src/prompt_energy/metadata.py: versions, hardware, Windows power observations.
- src/prompt_energy/records.py: schema validation and append-only persistence.
- src/prompt_energy/runner.py and experiments/run_p2.py: smoke scheduling,
  warm-up, correctness checks, resumability and determinism verification.
- tests/: HTTP fixtures, prompt snapshots, exact counts/unit conversions,
  extraction edge cases, schema, failure logging, interruption/resume behavior.
- docs/SPEC.md, REFERENCES.md, README.md, learning/P2.md: protocol, commands,
  verification evidence, five learning questions and assumptions.

Persist every raw HTTP response before interpreting/executing its text. Save
request settings, prompt, status/error, response body and timestamps. Transport
failures have no response body: record that explicitly, never invent one.
Warm-up is discarded only from scored results, never from the audit log.

Use append-only raw JSONL and result records with stable run IDs and an immutable
manifest containing schedule, settings, model digests and metadata. Fail closed
on conflicting manifests or damaged/truncated log records; do not silently edit
raw files. Reuse a saved raw response after interruption instead of generating
again. Skip completed results, including recorded failures. Export the SPEC CSV
schema with energy columns empty; keep additional API timing and metadata in
the raw record/manifest with explicit links. Difficulty_group stays empty.

## Proposed fixed extraction rule

Select the last complete fenced block labelled python, py, or unlabelled; if no
such block exists, use the entire stripped response. Do not merge blocks, repair
syntax, strip prose heuristically, install packages, or execute instructions.
Require a top-level function with the task's exact entry-point name; accept a
complete module only, not an indented body continuation. A fence without its
closing delimiter does not count as a complete block.

Failure order: API/transport failure; truncated (done_reason=length or the API
reports the 768-token cap reached); no_code for empty/no recognizable function
source; syntax_error for recognizable function source that does not parse;
no_code for a parsed module missing the required function; policy_rejected;
then test_failed, timeout, memory_limit or infrastructure_error from the P1 runner.
Preserve the detailed reason in the audit/result sidecar. Never test truncated
output as a successful generation even if it happens to contain runnable code.

## Risks and questions for the owner

- Approve the exact prompt text and proposed 4096 context / 8 CPU threads,
  extraction rule and smoke/determinism protocol before generation. These are
  prospective choices, not adjustments after observing model performance.
- Full-function extraction may penalize body-only responses; report this fixed
  rule rather than adding prompt-specific repairs after seeing results.
- Runtime prompt caching, model residency and model templates affect timing.
  Log raw fields and document caching; no energy claims are made in P2.
- The accepted P1 sandbox has Python-level network denial, not OS isolation.
  Its documented limitations remain unchanged; do not broaden its allowlist.
- Exact reference-length grouping details remain deferred and unimplemented.

## Validation and commits

Commit the reviewed registration before model calls. Run offline tests and Ruff,
then (after owner approval) the 35-row smoke and determinism check. Verify all
raw responses and failure rows are retained, API counts match, energy fields are
empty and a resumed run adds no duplicate completed jobs. Complete P2 only when
acceptance passes; record any unavailable runtime/model or blocked generation.
