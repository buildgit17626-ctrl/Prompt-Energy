# P3: estimating energy from a sensor log

Implementation is ready for owner review. No live pilot, warm-up or energy
measurement was started during this implementation. P3 acceptance remains pending
an approved pilot and inspection of real HWiNFO/CodeCarbon observations.

## What happens

The owner starts HWiNFO sensor logging at 500 ms, stays plugged in with Best
performance, and closes heavy background apps. The read-only preflight verifies
that CPU Package Power samples are fresh, correctly formatted and increasing.
The default prepare command only prints the registered 320-request schedule.
It does not contact Ollama or start CodeCarbon.

After approval, the pilot warms/unloads the models and measures 60 seconds of
idle power. It interleaves 20 tasks, four prompts, two models and two repeats
using seed 1729. Each request has an audited intent, exact saved response and
API timings. Testing occurs afterward in the existing restricted subprocess.
Failures remain rows. Five-second quiet gaps separate requests from previous
postprocessing. A resumed session measures a new baseline.

The integrator estimates the area under the CPU Package Power curve using
trapezoids. For example, 20 watts for 18 seconds is 0.1 Wh. A 5-watt baseline
over those same 18 seconds subtracts 0.025 Wh. We retain a negative adjusted
estimate if noise produces one; replacing it with zero would bias the data.

Total request energy includes loading. Primary post-load energy starts at
request start plus Ollama load_duration. Prompt and decode windows also use
Ollama aggregate durations. These are approximate boundaries, not measured phase
transitions. A mismatch larger than max(0.1 seconds, 5% of total_duration) gets
a flag. Short windows, absent coverage, sensor gaps and clock discrepancies get
flags too. Missing estimates stay empty, while low-resolution estimates remain
visible for review. CPU package power excludes most of the rest of the laptop.

CodeCarbon is an independent secondary estimate over a slightly wider task
envelope. It subtracts its own baseline and retains its native record. Its
Windows fallback assumptions may make it insensitive to workload; it cannot
validate precise input/output energy. No CodeCarbon phase values are invented.

## Files and commands

- experiments/config.py and docs/SPEC.md fix the protocol before the pilot.
- experiments/show_run.py displays a saved prompt, raw text, extracted code and
  recorded test outcome; it makes no inference request.
- experiments/run_p3.py exposes prepare, preflight, pilot and report commands.
- hwinfo.py parses and copies sensor evidence; energy.py integrates it.
- carbon.py wraps offline CodeCarbon; pilot.py journals and resumes execution.
- energy_report.py joins answer and measurement records into energy.csv and
  energy-summary.json. The latter reports load durations and repeat spread.
- tests/test_hwinfo.py, test_energy.py and test_p3.py use synthetic logs and
  fake clocks, model responses and trackers. They make no real model calls.

Raw evidence is append-only. Sensor mirrors preserve exact bytes and record
hashed prefixes. Keep the original live CSV for interrupted measurement recovery.
Only derived energy.csv and energy-summary.json are replaceable. Smoke and pilot
rows are excluded from the main research analysis. The full-run time estimate
is a four-arm pilot proxy, excluding several overheads, not a schedule guarantee.

## Five questions

1. Why divide watt-seconds by 3,600, and why subtract idle over each window's own duration?
2. Why is post-load energy only approximate even though Ollama reports load_duration?
3. What do low-resolution, sensor-gap and phase-sum flags mean, and which values remain missing?
4. How do saved raw responses prevent duplicate generation after an interruption?
5. Why must CodeCarbon use its own baseline, and why do smoke/pilot rows stay outside main analysis?

## Assumptions and outstanding validation

- The stated India location supplies country IND and UTC+05:30 defaults; the
  actual CSV timezone and dialect must be confirmed through preflight.
- HWiNFO exposes CPU Package Power in watts and the owner sets logging to 500 ms.
  The actual log path/version and internal sensor refresh rate remain unverified.
- A 60-second quiet baseline represents idle for that process session. Thermal
  drift and background activity can still change power later.
- Client and sensor clocks agree; aggregate phase durations approximate boundaries.
- The accepted P2 Ollama version/model digests remain installed. Changed versions
  require an explicit protocol decision rather than a silent resume.
- CodeCarbon's machine estimate may rely on fallback hardware assumptions.
- Two repeats estimate diagnostic spread, not reliable confidence intervals.
- This is a 320-request diagnostic pilot; full-run/difficulty analysis is later.
- New source fingerprints intentionally prevent resuming old P2 batches under
  altered code. Accepted P2 evidence is untouched; use its original commit for resume.
- The owner must approve the pilot before any live request. Offline tests cannot
  establish real sensor compatibility or complete P3 acceptance.
