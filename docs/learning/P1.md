# P1: understanding the harness

P1 builds the correctness-checking foundation. It does not ask Ollama for answers
or measure energy. Keeping those steps separate lets us establish that known
good programs pass and known bad programs fail before testing any model.

## How data flows

1. `experiments/config.py` records two model tags, seven prompt conditions,
   synthetic few-shot examples, seeds, resource limits and 40 explicit task IDs.
   Sampling uses a local random generator, so other random calls cannot alter it.
2. `tasks.py` checks the original archive's SHA-256, validates the 164-record
   population, and returns the selected tasks in registered order. Loading a
   task only reads strings; it does not execute a reference or a test.
3. A solution is a complete function module. For reference checks, HumanEval's
   function prompt and canonical body are concatenated without changing either.
4. `policy.py` checks the solution's syntax before starting a process. A rejected
   program receives a reason, rather than disappearing from the experiment.
5. `sandbox.py` creates a temporary directory and waiting worker. `windows_job.py`
   imposes memory/process limits before the parent lets the worker execute.
6. `worker.py` executes the candidate with restricted builtins and computation
   imports. It loads the benchmark check separately and passes the candidate
   function into it. The parent collects a structured outcome and cleans up.

A returned `passed` means all supplied assertions passed. A runtime error is
different from an assertion failure; both are different from a timeout or a
policy rejection. This distinction matters later when explaining a model's
verified yield. None of these P1 outcomes is an energy measurement.

## Why the unusual details exist

The Windows virtual-environment executable is a launcher that starts another
process. The sandbox launches the base Python interpreter directly so the
one-process limit does not reject its own worker. It still uses Python 3.11
and deliberately does not load installed site packages.

Python's -I flag ignores PYTHONHASHSEED. Instead, we construct a tiny environment
with a fixed hash seed and use -P/-s/-S to exclude unsafe import paths and site
startup. Both the random module and Python string hashing have fixed seeds.

One selected reference, HumanEval/160, calls eval to calculate arithmetic. We
retain that task and its unchanged reference, but supply an arithmetic-only
interpreter under that name. The same replacement applies to every solution.
It cannot evaluate calls or access files. This restriction must be reported
because it changes the supported Python environment.

Job Objects provide real resource limits, but they do not remove Windows file
or network permissions. AST checks are another layer, not a secure VM. The
exact limits and threat model are in `docs/SAFETY.md`.

## Verification

On Windows with Python 3.11.9:

- `python -m pytest -q --junitxml=results/P1-validation.xml`: **122 passed in
  44.69 seconds**. This includes all 40 references, all 40 deliberately wrong
  solutions, forced timeout/reaping, memory refusal, policy failures, seeded
  randomness, loader corruption/schema checks and infrastructure failure.
- `python -m ruff check .`: **All checks passed**.
- `python -m ruff format --check .`: **10 files already formatted**.
- `git diff --check`: no whitespace errors.
- `python -m pip check`: **No broken requirements found**. All 70 resolved
  dependencies are pinned in requirements-lock.txt. Imports of the fixed-stack
  libraries succeeded; see ENVIRONMENT.md for non-fatal cache/deprecation warnings.

The JUnit report is an automatically written, ignored local validation artifact.
An initial reference check exposed the eval restriction and Windows venv
redirector issue described above; both were fixed before this complete test run.
No study generations have been performed.

## Five questions to answer

4. Which restrictions does Windows enforce, and which are only Python checks?
5. Why would 40 tasks, two models, three repeats and these prompts produce 1,680

## Assumptions and deferred decisions

1. SPEC's code-generation study overrides the stale tabular-study description in
   AGENTS.md; its fixed library stack is nevertheless retained as instructed.
2. The provided CPU/RAM/no-discrete-GPU description is accurate. Power scheme and
   AC state were observed; the Windows Settings power-mode overlay was not.
3. Numeric task ordering, seed 1729 and sampling without replacement define the
   registered subset. Reference verification never changes that subset.
4. P3's one- and three-example variants are separate conditions. The three
   synthetic demonstrations are ordered and independent of benchmark answers;
   the one-example arm uses the first. Exact prompt text is fixed in config.
5. The pinned upstream benchmark and its tests are trusted data from the MIT
   source. Passing finite tests is not a proof of correctness; training-data
   contamination remains possible.
6. Five seconds and 256 MiB are uniform correctness-run limits, not model
   generation limits. Policy restrictions and the arithmetic-only eval mapping
   apply identically to all candidates and can reject valid unrestricted Python.
7. Windows 11 and CPython 3.11 are required for this runner; other platforms fail
   closed. The worker is resource-restricted, not an OS security sandbox.
8. The parent/worker API reports all outcomes; persistence of real generations,
   full result-row metadata, extraction failures and metrics belongs to P2/P3.
   P1 verification reports are software-test artifacts, not research observations.
9. P2 will fix num_predict, thread count and identical stop behavior before any
   generation. `num_predict=None` is a deliberate unconfigured marker, not an
   instruction to use an unlimited/default token budget. No HTTP runner exists yet.
10. Difficulty grouping, pilot-driven scale changes and other unresolved research
    choices require the owner's decision in later milestones. P1 makes none.
