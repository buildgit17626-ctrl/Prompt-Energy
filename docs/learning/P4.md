# P4: staged collection and analysis scaffolds

Implementation and synthetic verification only. No real P4 model requests,
warm-ups or baselines have been made. Live approval is still required.

## What was built

The full-run schedule has 840 requests. Stage 1 asks every registered task under
all seven prompts on both models once (560). Stage 2 adds two repeats for ten
seeded tasks (280). Its purpose is variability measurement. It is not pooled
into stage-1 hypothesis summaries, which would give those ten tasks extra weight.
The reduction from 1,680 requests was decided from timing feasibility, not quality.

A run-block invocation first checks AC/Best performance, Python, HWiNFO log
freshness/growth/cadence and registered runtime/model metadata. It saves unscored
warm-ups, unloads the models, waits five seconds and collects 60 seconds of idle
power. Requests are interleaved in the frozen stage order and separated by gaps.
The runner stops launching at three hours, finishes the current request, unloads
and collects the end baseline. It never starts the next block automatically.

The primary number is estimated whole post-load CPU package energy, both gross
and net of the block's starting idle rate. No input/output energy split is made.
CodeCarbon is absent from the execution path; its constant pilot power estimate
is documented as a limitation. Aggregate load time still makes the post-load
boundary approximate, and CPU package power is not whole-laptop electricity.

If the end idle rate differs by more than max(1 W,10% of start), the whole block
gets a drift flag. The starting correction is not replaced after seeing results.
A missing end baseline is flagged, not manufactured from a later block. Low
resolution and missing samples keep their existing flags. Negative net values
are kept. The all-row view and primary-low-resolution sensitivity view are both
produced; missing energy is never filled with zero and failures remain outcomes.

## Data flow and key files

- experiments/config.py: P4 schedule/limits/grouping and P4_ANALYSIS bootstrap settings.
- experiments/run_p4.py: prepare, preflight, run-block, report. Default is offline.
- src/prompt_energy/full_run.py: owner gate, blocks, request journals and recovery.
- src/prompt_energy/full_energy.py: gross/net integration and joined block flags.
- analysis/full_analysis.py: stage-1 summaries, ratios, joint token regression,
  residual/Pareto PNGs, stage-2 noise and optional frozen-group outputs.
- docs/SPEC.md: pre-registered research decisions and output schema.
- tests/test_p4.py and test_full_analysis.py: fake API/sensor/clock and statistical checks.

Raw responses are stored before parsing/testing. If the process stops after a
response was saved, resume uses it. A request intent without a response is
uncertain and must be investigated; it is never automatically repeated. The
original P1 subprocess remains responsible for candidate tests. Answers and
measurements are append-only. full.csv is a replaceable joined view so an end
baseline can add drift flags without changing earlier evidence. Complete resume
makes no API requests. Source/config changes reject resuming an old registration.

## How to read the analysis scaffolds

Bootstrap intervals resample task rows with seed 1729, 2,000 draws and 95%
percentiles. They are descriptive and do not erase dependence or small-sample
limitations. Missing counts accompany each statistic. Energy per correct answer
includes the cost of failures; if any relevant energy is missing, the full ratio
is unavailable instead of an optimistic partial ratio. Zero correct answers also
produce an unavailable ratio.

OLS includes input and output tokens and an intercept, separately by model.
Insufficient/rank-deficient data is reported. Correlation is not causal evidence.
Group comparisons use only labels frozen in the run manifest and omit P0. No
calibration labels or reference-length threshold have been supplied, so those
reports are explicitly unavailable. Stage-2 noise mixes output variation and
machine/measurement noise. The owner supplies interpretation in the report.
Load-duration summaries report counts, mean, standard deviation and range by
stage, model and prompt so loading overhead stays visible.

## Offline validation

Validation on Python 3.13.7 (64-bit): 325 tests passed; the final load-summary
change also passed all six analysis tests. Ruff reported no errors and all
40 Python files passed its format check. Synthetic Pareto/residual plots were
rendered and inspected. Recovery tests include saved-response interruption,
zero-request completed resume, uncertain intents, transport errors, missing
end baselines and a flagged ceiling overrun. No real P4 requests were made.

## Five questions

1. Why are the extra repeats kept out of stage-1 hypothesis summaries?
2. Why does net energy keep the start baseline even if the end baseline drifts?
3. What is the difference between a saved response and an uncertain request intent?
4. Why can missing energy make energy-per-correct unavailable even when some tasks passed?
5. Why do we omit phase attribution and exclude P0 from difficulty-group comparisons?

## Assumptions and outstanding items

- Owner approved the subset seed, stage separation, block endpoint rules, drift
  threshold and bootstrap settings before implementation; live approval absent.
- HWiNFO remains at 500 ms with the registered dialect/offset and version; laptop
  stays plugged in, Best performance, awake and otherwise quiet. The runner does
  not change system power settings. Sleep/kill/network-service errors can leave
  incomplete blocks, which are retained with flags.
- The beginning idle rate represents the block for net correction. End drift is
  diagnostic and does not justify retrospective baseline replacement.
- Four hours is an execution safety ceiling with bounded requests and closure
  reserve; OS suspension or an external stall can cause a flagged overrun.
- Prior P2/P3 evidence is immutable and excluded from hypothesis scaffolds.
- Group maps/rules must be supplied and frozen before the main run for planned
  group comparisons. No calibration run or grouping threshold is invented here.
- No new dependencies, full-run generations or written scientific interpretation.
- Full live acceptance remains pending owner approval and execution; synthetic
  validation is not evidence that an overnight hardware run has completed.
