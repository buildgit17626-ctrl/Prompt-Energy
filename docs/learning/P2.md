# P2: from a fixed question to an auditable result

P2 automates local inference and correctness checks. It does not measure energy,
perform the full study, or assign difficulty groups. A model answer may fail;
successful harness operation means that answer and its failure are retained.

## How data moves

1. The loader checks the pinned HumanEval archive and reads the registered tasks.
   The prompt builder adds the selected instruction and zero, one or three
   original examples. Tests and reference solutions are never model input.
2. The runner records the runtime version, exact model digests, templates,
   decoding settings, Python/library versions and observed host/power state.
   It saves a seeded shuffled schedule before generating any answer.
3. One READY warm-up per used model per process session is saved but unscored.
   Two identical P0 requests per model check exact text equality and compare
   native prompt counts/durations. A lower count OR duration on request two
   triggers keep_alive=0 for every scored request. A timing decrease may just
   be noise; this is a conservative operational rule, not proof of caching.
4. The cache decision is saved before the smoke. With zero selected, models are
   explicitly unloaded and absence is checked before scored requests. Every
   load_duration is still saved. This changes loading overhead and must be
   considered before defining the later energy measurement boundary.
5. Each HTTP request has a durable intent record. The exact response bytes,
   HTTP status and start/end timestamps are saved before interpreting output.
   Token counts and durations come directly from Ollama, not word counting.
6. The extractor selects the last complete eligible fenced block defining the
   required function, or the whole stripped response. It adds the task prelude,
   then the restricted subprocess executes benchmark checks. No code repair or
   prompt-specific retry is allowed. Truncated answers cannot count as passes.
7. A result row and detailed reason are appended. CSV is a derived view of the
   result journal. Energy and difficulty cells are empty because P2 did not
   measure or assign them. Candidate test time is outside request wall time.

## Key files

- experiments/config.py and docs/PROMPTS.md: registered experimental choices.
- src/prompt_energy/ollama.py: loopback transport and native field validation.
- src/prompt_energy/runner.py: schedule, probes, warm-up, requests and resume.
- src/prompt_energy/records.py: locking, durable journals and exact CSV schema.
- src/prompt_energy/evaluation.py: fixed failure classification and sandbox use.
- src/prompt_energy/metadata.py: observed hardware, versions and power state.
- experiments/run_p2.py: owner-facing command; no full-run or energy option.
- tests/test_p2_runner.py: offline fixtures, schema and interruption tests.

The batch directory holds manifest.json, cache_policy.json, requests.jsonl,
raw.jsonl, sessions.jsonl, results.jsonl and the derived results.csv. Raw body
bytes are stored as base64, so even HTTP errors or partial responses are retained
exactly. Each generation has a stable ID linking the files. These logs are
git-ignored and should be backed up unchanged; the code repository alone is
not a backup of experimental data.

## Resume is not a retry policy

Repeating the command with the same folder skips completed successes AND
failures. If raw output exists without a result, the saved output is evaluated
without another generation. An interrupted request whose response was not saved
is uncertain: the runner stops rather than concealing a second attempt. Corrupt
JSONL, duplicate IDs, changed registration or runtime/model metadata also stop
the run. File locking prevents two runners using the same folder concurrently.

## Five questions to answer

1. Why must we save raw output before extracting code or checking correctness?
2. How do warm-up, determinism probes and scored requests differ in the dataset?
3. Why do fixed seeds and temperature zero still require an observed text check?
4. Why does resuming skip a failed answer, and when must it stop instead?
5. Why are separate input/output timings insufficient to claim separate measured
   input/output energy, particularly when model loading occurs on each request?

## Verification

Before live generation: Python 3.13.7; 247 tests passed; Ruff check and format
check clean. All 40 reference solutions pass the registered extraction/prelude
path. After live acceptance and additional cache/error regression tests, the final
suite passed **255 tests in 27.74 seconds**, with no warnings. Ruff check passed
and all 21 Python files passed the format check. Report: results/P2-final-tests.xml.

Observed determinism pairs on Ollama 0.40.6 (2026-10-19):

| Model | Identical text? | Input count, first / second | Prompt time in seconds, first / second |
| --- | --- | --- | --- |
| 0.5b | No | 145 / 145 | 0.465803 / 0.014990 |
| 1.5b | No | 145 / 145 | 0.886607 / 0.062011 |

Both pairs triggered the registered duration-decrease rule, so scored
keep_alive=0 was frozen before the first smoke request. Native raw responses
also expose prompt_eval_cached_count: 15 on each first probe and 144 on each
second probe. This additional observation supports reuse; it was not used to
change the preregistered decision rule. The paired texts were not identical:
temperature zero and seed 1729 did not guarantee identical text on this runtime.
No output was replaced or repaired to make the check appear deterministic.

The live 1.5b smoke completed all **35** registered task/arm combinations:
**31 passed and 4 test_failed**. This is harness acceptance evidence, not a
research comparison of prompts. Both warm-ups and all four determinism outputs
are retained separately from the 35 scored outputs. All 35 scored raw responses
reported prompt_eval_cached_count=0.

The post-run audit checked each prompt/options payload against config, all
CSV fields against result JSONL, token counts/rates against native API fields,
and all energy/difficulty fields for emptiness. Resume completed with zero
new requests; SHA-256 hashes of every journal, manifest, cache decision and CSV
were unchanged. Evidence: results/P2-acceptance.json, with a committed copy at
results/samples/P2-acceptance.json. Original generations remain under
results/p2-smoke/ and are git-ignored. No HWiNFO or CodeCarbon measurement ran.

## Assumptions and limits

Owner-requested review after acceptance: `python -m experiments.show_run smoke-026`
now displays a recorded prompt, response, extracted/combined source and saved
test result without model calls or execution. See P2_SMOKE_REVIEW.md for all four
failed answers and two passing verbose answers. Independent sandbox replays
confirmed algorithm errors, with no extraction/prelude bug in these six rows.
The original logs and the verified copy outside the repo are unchanged.
The extended suite passes 261 tests; Ruff and formatting checks are clean.
SPEC now excludes smoke data from research analysis and records prospective
approximate P3 energy windows and the owner's approved timing tolerance.

- Windows 11, Python 3.13 (64-bit), the installed Ollama API and both registered
  model tags are available; CPU-only options are requested. No new dependencies.
- The owner does not send competing Ollama requests during a batch. The harness
  lock protects its own output directory, not other applications or directories.
- Ollama's native counts and durations are authoritative runtime measurements.
  They are not independently reconstructed tokenizer counts or energy readings.
- The conservative cache rule is fixed before outcomes; it may unload even
  when a shorter prompt time is merely noise. It does not prove text determinism
  for every task or hardware/runtime configuration.
- Full-function extraction, policy restrictions and the 768-token cap can make
  otherwise useful answers fail. Report these failures; do not tune them away.
- The accepted P1 sandbox is not an OS security boundary; see SAFETY.md.
- This 35-request smoke validates operation, not hypothesis support. The owner
  still chooses grouping details and writes the later research analysis.
- No energy claims, full-run timing promises, or difficulty labels are inferred
  from this milestone. P3 is separate and requires owner authorization.
